# Code map

## Crates (`crates/`)
- `proto` (`guilab-proto`): control protocol types (`Request`/`Command`/`Response` + reply structs, `Command::access()` for the lock rules), socket paths, blocking `Client`. `input.rs`: the `input` grammar (`Action`, `parse`, `Display`, and `HELP`, which is `guilab input --help`). Event log, pure logic so it's unit-tested cheaply here: `events.rs` (`Event`/`EventData` kinds, `default_tier`, `Tiers` overrides, kind groups, `Delivery`), `log.rs` (`EventLog`: append, motion/scroll coalescing, per-key delivery cursors, `query`), `text.rs` (`Fmt`: all event text, human input run summaries; shared with the future viewer feed). `Command::log_text` = how a command appears in the log. serde only, has the cheap unit tests.
- `compositor` (`guilab-compositor`): smithay. `Session` = one Wayland display. No IPC, no CLI.
  - `session.rs`: `Session` struct, globals, socket, seat, output. `Session::new` returns the session plus its own `EventLoop<Session>`.
  - `handlers.rs`: all smithay handler traits except xdg-shell and X11, `delegate_dispatch2!`, surface ids (`SurfaceId` in each surface's data map, assigned in `new_surface`), dmabuf blocker pre-commit hook, `SelData` (owner of a compositor-side selection: `clip set` text or an X client).
  - `shell.rs`: xdg-shell + decoration. Window policy, focus and stacking for Wayland and X windows (`focus_window`, `parent_window`, `move_window`), popups (anvil's unconstrain + grab), `relayout` after output changes.
  - `xwayland.rs`: per-session Xwayland + `XwmHandler` (from anvil's `shell/x11.rs`): spawn on our display range, X window policy (`x_place`), override-redirect stacking (`xw.or`), clipboard/primary bridging.
  - `focus.rs`: `KbFocus` (keyboard focus: `WlSurface` or `X11Surface`; the X arm does SetInputFocus/WM_TAKE_FOCUS). Pointer/touch focus stay `WlSurface` (smithay's X11Surface targets only forward to it; X menus grab inside Xwayland).
  - `cursor.rs`: the apps' cursor (`AppCursor`: named, hidden, or a rendered cursor surface), theme cursors, drawing it into `screenshot --cursor`.
  - `frame.rs`: `tick()` (render, presentation feedback, frame callbacks), settle detection, PNG writing, `set_output`.
  - `render.rs`: `Gpu` (GLES on a render node, pixman fallback; `GUILAB_RENDERER=pixman|/dev/dri/renderD*`), per-session offscreen `Frame` with a damage tracker.
  - `tree.rs`: `tree` reply; `track_windows` (each tick) diffs toplevels to log window open/close/title. `procs.rs`: run/kill/ps and cleanup; logs app exits (`reap`).
  - `Session::log` (`EventLog`) holds the session's events; the compositor logs human input, windows, app exits; the server logs the rest.
  - `input.rs`: `InputEvent` + `Session::inject(ev, InputSource)`, the only path from any input to the seat; logs `Human` input (output pixels, keysym name + typed char, window under the pointer). Hit-testing, click-to-focus, held buttons/touches (`release_all`), popup-grab workarounds.
  - `actions.rs`: input chains (`Chain::new(actions, source)`: agent `input`, or the human's via `guilab debug input`): proto `Action`s -> events. `run_chain` returns `Some(delay)` at sleeps/glide steps; the server resumes it. Output pixels -> logical here.
  - `keys.rs`: keysym lookup over the seat keymap (key + Shift/AltGr), key name aliases, and the extended keymap for typing characters the keymap lacks.
  - `clipboard.rs`: `clip set` (server-owned selection, written from a thread, announced to the X11Wm) and `clip get` (own text, or a pipe from the owning Wayland client or X11Wm).
- `server` (`guilab-server`): the daemon. Outer calloop loop: control socket, connections, a 16 ms timer, signals, each session's nested loop. `requests.rs`: request dispatch, session resolution, lock check, logging commands and their events, `new`, deferred replies (screenshot waiters, input jobs, clipboard pipes, `new -x` waiting for Xwayland, polls; all checked from the tick). Every reply to a session command goes through `Server::attach` (adds the client's undelivered events; key = token or anonymous). Polls (`PollWait`) fire from `check_polls`; a poll whose client hung up is dropped (read returns EOF). `lock.rs`: `LockState` (take/release/check, and `revoke`/`set_shared`/`human_input_allowed` for the viewer). The viewer should call `Server::revoke_lock` / `Server::share` (they log the events), not `LockState` directly.
- `guilab`: the binary. `main.rs` (clap CLI; hidden `debug` = the human's actions; local UTC offset via libc for event times), `client.rs` (connect + autostart, stale-server warning, `server`), `format.rs` (text output; delivered events go to stderr, poll output to stdout). Integration tests in `tests/it/` (one test binary).
- `viewer` (`guilab-viewer`): the viewer window, see `viewer.md`. Generic part (no guilab types; an egui host for any smithay program): `source.rs` (calloop source for the host connection whose errors stay local), `host.rs` (sctk window, dmabuf/shm presentation, host input → ordered `HostInput`), `gfx.rs` (egui_glow painter on smithay's GL context, mirror textures). guilab part: `ui.rs` (`ViewerUi`: tabs, session view with zoom/pan/input forwarding, lock bar, and per session (`PerSession`, keyed by name, reset when the session key changes) a `Sketch` + `Chat` from markup in a left and a bottom panel; `SessionView` in, `Action` out: input, revoke, share, `Freeze` (a drawing wants a screenshot), `Message`) and `lib.rs` (`Viewer`: draw scheduling, key routing, `feed_next`/`push_feed`/`set_screenshot`). Depends on smithay and markup, not on the compositor or server.
- `markup` (`guilab-markup`): drawing on screenshots, the queue and the chat panel as plain egui widgets; depends only on egui, so it can be copied into another egui app. `mark.rs` (tools, palette, `Mark` -> egui shapes through an `Xf`), `raster.rs` (`Renderer`: CPU composite by tessellating those shapes with epaint and rasterizing the triangles, font atlas included; `downscale`), `sketch.rs` (`Sketch`: toolbar, `canvas(ui, View)` over the host's image rect, text editing, queue strip, `take_all` -> `Annotated { image, preview, notes }`), `chat.rs` (`Chat`: feed of `FeedItem`s + message box -> `Outgoing`). Unit tests (`tests.rs`) drive it with a bare `egui::Context`; `examples/compose.rs` composites marks onto a PNG standalone (handy for making annotated samples).
- Server side of the viewer: `server/src/viewer.rs` (`ViewerState` Hidden/Connecting/Shown, `show`/`hide_viewer`/`viewer_tick`, builds `SessionFrame`s from slots, applies `Action`s: input through `Session::inject(.., Human)` gated by `human_input_allowed` except releases, `revoke_lock`, `share`, `Freeze` -> `Session::read_rgba` -> `set_screenshot`, `Message` -> `requests::human_message` with PNG pixels and annotations). Each tick it feeds new message/say/command events to the viewer (`feed_items`, via `EventLog::from_seq`; PNGs decoded here).

## Runtime layout
`$XDG_RUNTIME_DIR/guilab/`: `control.sock`, `server.lock` (flock: one server per runtime dir), `server.log` (autostarted server's stderr), `s/<session>/` = the session dir: `wayland-0` socket, `app-N.log`, `xwayland.log`, default screenshots `shot-N.png`, message attachments `msg-SEQ-N.*` (human) and `say-SEQ-N.*` (agent). Xwayland uses the machine-wide `/tmp/.X11-unix/X<n>` + `/tmp/.X<n>-lock` (n from 100; smithay writes our pid in the lock and reclaims locks of dead pids, so a crashed server's leftovers get reused) plus the abstract socket. The session dir is the apps' `XDG_RUNTIME_DIR`, so apps don't see the user's bus, pipewire or compositor. It's deleted when the session ends. Socket paths must stay under 108 bytes, hence session names are capped at 32 chars and tests use `$XDG_RUNTIME_DIR/glt-*` rather than the scratchpad.

## Event loops
- Server loop data is `Server`. The viewer's host connection (`HostSource`) and the connect-result channel are sources in the server loop. Each session's `EventLoop<Session>` is inserted as a `Generic` source (an EventLoop is `AsFd`); on readiness the server dispatches it with `&mut slot.session`, then flushes clients. The session's display, socket, pidfds and dmabuf blockers are sources in the session loop.
- **Never put a calloop `Timer` in a session loop**: calloop timers live in the poll timeout, not in an fd, so they never wake the server loop. Timed work goes through the server's 16 ms tick (`Server::tick`: session `tick()`, `reap_tick()`, screenshot waiters, graveyard, TTL/idle once a second).
- No source closure in a session loop may capture its `LoopHandle` (Rc cycle, the session would leak). Use `s.handle` from the `&mut Session` argument.
- smithay APIs taking `LoopHandle<'static, D>` (e.g. `X11Wm::start_wm`) get `session.handle`.

## Behaviours worth knowing
- Settle (`Session::settle_state`): a toplevel has a buffer, no configured-but-unmapped toplevel, no unanswered configure (not acked, or acked but not yet committed: GTK acks a scale change and commits ~20 ms later; ignored once `CONFIGURE_WAIT` = 1 s passed since we last configured, because clients may ack without committing), 150 ms without commits, and a render after the last commit. The server caps waits at 3 s (10 s before the first window). Animated apps always hit the cap.
- Apps get their own process group and `GUILAB_TAG=<tag>`. Kill = SIGTERM to the group, SIGKILL after 2 s. Ending a session also signals every process carrying the tag (`/proc/*/environ` scan), like guibox. Apps die with the server via PDEATHSIG.
- The server blocks SIGTERM/SIGINT/SIGHUP (calloop signalfd) and ignores SIGPIPE; `std::process::Command` doesn't reset either, so `spawn` clears the mask in `pre_exec`. Without that, apps ignore SIGTERM.
- At fractional scales a tiled window can be one pixel larger than the output (500 px / 1.5 = 333.3 logical, rounded up to 334). `tree` reports it honestly.
- `tree` lists toplevels topmost first, coordinates in output pixels (edges rounded half-down).
- Window policy: a parentless toplevel tiles if no other tiled one exists; otherwise it floats, centered, with `bounds` = output (so an oversized default size fills the output anyway).
- Popups are positioned by smithay's positioner (flip/slide/resize) against the output, relative to their parent window.
- Stacking: floating windows always above tiled, dialogs above their parents (`focus_window`), X override-redirect windows above all (re-raised in X order after every restack). Click/touch-down focuses and raises, unless a grab is active; override-redirect windows never take focus. `Space::map_element` always raises, so moving a window goes through `move_window`.
- X windows live in the same `Space<Window>` (`Window::new_x11_window`), so rendering, hit-testing, `on ID` and screenshots need nothing special. Space position = X position (`configure_notify` keeps them in sync), which X menus rely on. X surfaces get a new wl_surface (and so a new `tree` id) on every map; the xid stays. Settle counts mapped X windows: one without a buffer yet is "drawing".
- Xwayland lifetime: it lives in the session loop as the `XWayland` source; dropping the loop (session end) removes lock and sockets and closes its Wayland connection, which makes it exit. It carries the session tag. If it dies, `XwmHandler::disconnected` drops X windows and the session stays up without X.
- Settle treats delivered input like a commit (`last_input`), so a screenshot right after `input` waits for the app to react.
- Popup grabs (smithay, spec-conformant): clicks on the popup client's own surfaces don't dismiss; the client closes its menu itself. smithay quirks worked around in `input.rs`: an ended popup pointer grab swallows the next motion (we resend it); the popup keyboard grab keeps focus on the dead popup until the next key (`popup_may_close` hands focus back; chains wait up to 500 ms before keys after a click while a menu is open, or the keys go to the closing menu).
- Typing: characters on the keymap use their real keys (+Shift/AltGr), but only keycodes <= 255 (X can't see higher ones; `us` has EuroSign only on 443). Others: the seat keymap is swapped for one with them added on spare keycodes <= 255 (16 in `us`), sent to all clients of the session. The extended keymap stays active afterwards (its other keys are the base keys) and is only replaced when other extras are needed: swapping straight back made X clients (Xlib reads ahead) look up the typed keys in the restored keymap. Runs of more than 16 new characters swap again, with 100 ms between swaps when an X window has focus. Replaces smithay's `inject_text_keysyms` (its codes start at 9 = Esc for raw-keycode clients).
- Input chain sleeps resume from their scheduled time, not from the tick that ran them (else 16.7 ms glide steps took two 16 ms ticks each and glides ran at half speed).
- Lock tokens: 8 chars from `/dev/urandom`. Unlock/revoke/force-takeover abort the session's queued input chains with an error.
- Edition 2024 `if let` keeps temporaries alive through the block: `if let Some(w) = self.space.elements().find(..).cloned() { self.space.map_element(..) }` fails to borrow-check; bind the result first.

## Build and test
- smithay is git master pinned in the root `Cargo.toml` (crates.io 0.7 lacks `delegate_dispatch2!`, `inject_text_keysyms`, etc.). Bump the rev deliberately.
- Only `cargo test --workspace` (narrow with `--test it <module>::` or a name filter) and `cargo clippy --workspace --all-targets`. No `-p`, no feature flags, no per-command env (each combination builds another copy of the tree). Dev profile only; deps at opt-level 2, line-tables debuginfo, compressed debug sections (`.cargo/config.toml`).
- compositor, server and viewer libs have `test = false`: each lib test binary would link all of smithay. Prefer integration tests in `crates/guilab/tests/it/`, or unit tests in `proto` and `markup` (egui only, cheap).
- `events.rs` tests use `guilab debug` for the human side and need no app except `window_events` (GTK4). Integration tests start a private server per test (`Lab`, runtime dir `$XDG_RUNTIME_DIR/glt-<pid>-<n>`) and skip tests whose apps aren't installed. Xwayland tests (`xwayland.rs`) skip without Xwayland or tkinter. Test apps: `tests/it/apps/tk_app.py` (Tk, pure X11: entry, a menu button posting an override-redirect menu, a transient dialog), `gtk_app.py` (PyGObject GTK4: `--menu` popover in the bottom-right corner, `--dialog`, `--second`), `gtk_cursors.py` (named / image / hidden cursor areas), `gtk_input.py` (entry, button, double-click/context-menu area, scroll list, DnD, zoom gesture; `--floats`), `qt_app.py` (PySide6: line edit, right-click QMenu, `--menu`). The input apps print each event and their widget positions (`pos NAME X Y W H`) to their log; tests read it (`input.rs` `wait_log`, `center`).
- Numbers (24-core machine): clean build ~75 s; no-op 0.05 s; one-line edit in compositor or server + test build ~0.6 s; `cargo test --workspace` runs in ~7 s (tests run in parallel; the slowest are the GTK input and viewer ones); `target/` ~2.7 GB. 3x worse at low load means something's wrong.
- Forcing toolkits onto X in a `-x` session: `GDK_BACKEND=x11`, `QT_QPA_PLATFORM=xcb` (we set `wayland` only if unset), `chromium --ozone-platform=x11`.
- `viewer.rs` tests need GLES (skip otherwise) and use a second server as the viewer's host. `GUILAB_VIEWER_SHM=1` in the server's environment forces the shm path.
- Manual testing: the CLI against the real runtime dir works fine; `guilab server --stop` after rebuilding (the CLI warns when the server's binary is older than itself). `GUILAB_LOG=warn,guilab_compositor=trace guilab server` runs a foreground server with commit tracing.
