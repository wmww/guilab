# guilab design

guilab lets humans and agents work on a GUI app together. It replaces the gui-testing skill (`~/agent-skills/gui-testing`: `guibox` wrapping headless sway + grim + wdotool). It must do everything guibox does (disposable headless sessions, screenshots, mouse/keyboard input, resize/scale, Xwayland, independent parallel sessions, automatic cleanup) as one self-contained package with no external tools. On top of that it adds a human-facing viewer with chat and drawing over screenshots. Drawing is the most important extra.

Plan steps 1-7 (skeleton, headless compositor, input and locking, Xwayland, event log, viewer window, chat and drawing) are built; see `plan.md` for what's next and `code-map.md` for the code.

## Stack
- **Rust**, one `guilab` binary for both the server and the CLI. Split into workspace crates if it helps build times (see the reasonable-rust-builds skill).
- **smithay** compositor in-process. guilab *is* the compositor, so screenshots read our own buffers, input is injected directly (touch included), and frame timing is under our control.
- Reuse existing code for tricky logic (popup placement/constraints, Xwayland WM, grabs) rather than writing our own: smithay helpers first, then anvil (MIT), then cosmic-comp/niri.
- **egui** for the viewer, drawn with the same GLES renderer as the sessions (so session frames are GPU textures; the visible one is GPU-copied into an egui texture when it changes) and presented to the host as dmabufs (shm CPU copy as fallback).
- GLES renderer on a DRM render node, pixman software fallback for sessions. The viewer needs GLES (egui has no software renderer): on a pixman server it gets its own GLES on Mesa's software EGL device (llvmpipe) and session frames are uploaded from the CPU.
- Details and verified APIs: `smithay.md` (core compositor), `viewer.md` (viewer window, egui).
- Public repo. MIT by default; switching to GPL is fine if borrowing from cosmic-comp/niri needs it.

## Server
- Runs without any parent Wayland connection. The viewer window is optional: `--show` at startup, `guilab show`/`hide` at runtime. Opening or closing the host connection never affects sessions. Host disconnects, protocol errors and closing the window close the viewer only, and never stop the server. `show` sends the CLI's own `WAYLAND_DISPLAY` (as a socket path), since the auto-started server's environment may be stale; it replies once the first frame is up, and refuses the server's own session sockets.
- While the viewer is hidden, the server's own clock drives frame callbacks, so apps behave the same either way.
- Starts automatically on the first CLI command that needs it, and then exits after 10 minutes without sessions. `guilab server --stop` stops it (ending all sessions).
- Sessions end after an idle TTL (default 30 minutes without commands targeting them; `new --ttl SECS`, 0 = never). Ending a session kills everything spawned in it, including double-forked daemons.
- Each session has its own dir, which is also its apps' `XDG_RUNTIME_DIR` (Wayland socket, app logs, screenshots). Apps don't see the user's D-Bus, audio or compositor.
- Each session runs a private `dbus-daemon` (`compositor/src/bus.rs`, socket `<session dir>/bus`, apps get `DBUS_SESSION_BUS_ADDRESS`): GApplication uniqueness works and the "Unable to acquire session bus" noise is gone. Its config has no service dirs, so nothing is ever activated (no portals, settings daemons, AT-SPI; asking apps fail fast). It carries the session tag and is killed and reaped with the session. Apps get `GTK_A11Y=none` and `NO_AT_BRIDGE=1` unless set, since there's no accessibility bus; an AT-SPI bus on it is the way to the accessibility tree later. Without dbus-daemon installed, sessions just have no bus.
- **Multiple sessions per server.** Each session has its own Wayland display socket, output, seat, Xwayland and app processes. Clients see only their own session. Each session is its own smithay state type (`Display<Session>`, handlers on `Session`), not one shared state with lookups, and has its own calloop loop (data = the session) nested in the server's loop, which is what X11Wm and smithay's per-display getters need.
- **Window policy:** the first toplevel fills the output (tiled states, no decorations). Dialogs (with a parent) and later toplevels float centered on top, cascaded (32 px steps down-right) where they would hide or be hidden by another float entirely, so every window stays reachable. Floats keep their offset from the center as they or the output resize; title-bar drags (`xdg_toplevel.move`, X `_NET_WM_MOVERESIZE`) move them, kept on screen. No interactive resize. X windows follow the same rule (transient, modal or non-Normal window types float); X override-redirect windows (menus, tooltips) go where X puts them, above everything.
- **Xwayland** (smithay's X11Wm) is opt-in per session: `new -x` starts it and replies once it's ready; apps then get `DISPLAY`. Not on by default: it costs startup time and memory, and with `DISPLAY` set, apps that support both may silently pick X11 when the agent meant to test Wayland. Not lazy (spawn on first X connection): smithay's `XWayland::spawn` owns the listening sockets, so that would mean reimplementing it. Display numbers come from `:100` up (smithay alone stops at `:32` machine-wide).
- X apps render at the output scale: Xwayland's client scale makes X pixels = output pixels, and toolkits are told via XSETTINGS (`Xft/DPI`, GTK3's integer `Gdk/WindowScalingFactor` + `Gdk/UnscaledDPI`, updated live) and `Xft.dpi` in RESOURCE_MANAGER (read at app start). GTK3, Qt and Tk come out sharp and the right size (GTK3 at fractional scales: bigger fonts, unscaled widgets); apps that ignore DPI (xeyes, core-font xterm) are small. The root cursor is the theme's default arrow at that scale. X clients may always read the clipboard (no focus check): sessions are disposable and scripts like `xsel` have no window.
- Key repeat is client-side and per seat: the session sends repeat rate 0 while agents type (a held key in an input chain must not repeat) and turns it on (25/s, 600 ms) when human keys arrive from the viewer.
- Floating windows always stack above tiled ones, and dialogs above their parents; clicking a window focuses and raises it within that order.
- **Session resolution:** `--session NAME` > `$GUILAB_SESSION` > the session created from the cwd's git worktree root > the only session, if there's exactly one. A new session defaults to the worktree's name. Goal: one agent per worktree, each with its own session, and no naming needed.

## IPC
- One control socket per server, under `$XDG_RUNTIME_DIR/guilab/` (or `$GUILAB_DIR`, for a second server such as guilab nested in a guilab session), using line-delimited JSON requests and responses. Each request names its session.
- The CLI is the only client. No MCP.
- Versions: every request carries `proto` (`guilab_proto::PROTO`, bumped by hand on incompatible changes). The CLI pings first on every command: another `proto` is an error saying to restart the server (`server --stop`) or use its binary; another GNU build id (read from the loaded ELF notes, `guilab/src/build_id.rs`) is a warning. The server also rejects requests with another `proto`, except `ping`/`shutdown` (so `server --stop` reaches any server).
- `GUILAB_NO_AUTOSTART=1` makes a CLI fail instead of autostarting a server; `server --wait` blocks until one answers. Apps never inherit `GUILAB_DIR`/`GUILAB_SESSION`/`GUILAB_TOKEN`/`GUILAB_NO_AUTOSTART`, so a guilab run as an app gets its own server.

## Locking
- `guilab lock` returns a short random token. One holder per session, so two agents can't drive the same session. `lock` again with the token returns the same token; `lock --force` takes over (the old token stops working); `unlock` releases everything still held (keys, buttons, touches).
- `lock` and `input` also need the agent to be marked working (`guilab work`, see "Agent status"); `done` releases the lock, with or without the token.
- `input` always needs the lock (it competes with the human's input). Other changing commands (run, kill, output changes, clip set, end) need the token only while the session is locked. Read-only ones (screenshot, tree, ps, clip get, log, poll) never do. Why not lock for everything: the build/kill/run loop and scripts on an unlocked session stay token-free, and run/kill don't fight the human's input. A stale or revoked token is always an error, so an agent learns it lost the lock.
- Token passing: `-t TOKEN` on any command (agent shells don't keep env between calls) or `$GUILAB_TOKEN`. Errors say exactly what to run.
- While locked, the human's input to that session is blocked. They can still view, screenshot, draw and send messages. Their only lock control is **Stop** on the lock toast (revoke): it drops the agent's lock, and its token stops working until it locks again. There's no sharing (human and agent driving the app at once): it only confused both.

## Event log
- Each session has an append-only, timestamped (unix ms), numbered (`seq`) log: agent commands with args, human input, app start/exit (code, signal, after `kill` or not), window open/close/title (toplevels and X windows; diffed each frame), output changes, lock/unlock/revoke, human and agent messages, agent status (`work`/`done`), screenshots, the expiry warning. In memory, capped at 100k events (oldest dropped); it dies with the session.
- Human input is logged per event, with motion coalesced into one event per run (`path` of `[x, y, ms]`, new run after a 500 ms gap or any other event) and consecutive scrolls summed. Touch logs finger down/up (the text pairs them into "tapped at" / "dragged finger N from A to B"; intermediate motion isn't logged). Touchpad gestures are logged once, when they end, with totals (`dx`/`dy` in pixels, final pinch `scale`, `cancelled`). Keys are logged as keysym name + character: the session keymap is plain `us` without options and there's no input method, so there are no dead keys or compose sequences to turn into text. Agent input is logged only as its `input ...` command.
- Window close events say who closed it (`by`), from the client's pid (`_NET_WM_PID` for X) when the window disappears: `exit` (process gone or zombie), `kill` (its process group got `guilab kill`), else `app` (the app closed it while running, e.g. its close button).
- Three tiers:
  - **Wake:** ends a blocking `poll` (or emits a `--follow` line). Defaults: human message, lock revoked, app exited or crashed on its own, session about to expire (warned `min(60 s, ttl/2)` before; a waiting poll doesn't count as activity, so the warning reaches it and the agent can keep the session alive).
  - **Passive:** rides along with the next delivery. Defaults: human input, windows, output, app start, app ended by `guilab kill`, lock/unlock.
  - **Log:** only in `guilab log`: the agent's own actions (commands, its messages, `work`/`done`, screenshots).
- A delivery is a poll result or the reply to any agent command (not `log`, `poll` itself or the human's actions). It carries every non-log event since that client's previous delivery, except events its own commands caused (each event records the delivery key that caused it; e.g. its own `run` doesn't come back as "app started"). Replies print them on **stderr** (`[guilab events since your previous guilab command at HH:MM:SS; not errors]`), so stdout stays parseable; `--json` puts them as one JSON line on stderr.
- **Human messages are an inbox, not a stream** (agents trim and discard stderr; a message delivered there was lost once). Command replies never include them, only `unread` (count, first time), printed as `[guilab: a human message waiting since HH:MM:SS; read it now: guilab poll]` on every reply until a poll prints them. Unread is per session, not per key (one agent per session), so any poll shows them once and marks them read; `has_wake` counts unread messages, so that poll returns at once.
- **Delivery keys:** requests from the session's own worktree or from outside git share the default key; a request from another git worktree (another agent, using `-S`) gets that root as its key. So an agent that changes directories or mixes `-t TOKEN` and plain commands has one cursor (separate cursors showed every event twice). A new key starts at the default key's position. 32 keys kept per session, least recently used dropped.
- **Several pollers on one key:** each wake event reaches all of them (a poll fires on any wake event after it started, even if a sibling already consumed it); passive events go to whichever delivery comes first.
- `poll --wake`/`--passive KINDS` override tiers for that poll only (kind or group names: `input`, `window`, `app`, `agent`, `all`). Use this tier split anywhere new event kinds appear, rather than ad-hoc rules.
- Text output (`proto/src/text.rs`) is written for agents reading it cold and was checked with context-free sub-agents: chronological, one line per event, human input runs merged into one line of phrases (`double-clicked at X,Y in window 7; typed "hi"; pressed ctrl+s; dragged from A to B; tapped at X,Y`), messages in full with each image's element listing, a fetch hint and a `guilab done` hint. Pointer noise is collapsed: a move is kept only where the pointer comes to rest at the end of a run (clicks, drags and scrolls carry their own position), and scrolls with only moves between them add up. `log -n N` doesn't count motion events, and repeats the "N earlier events not shown" note at the end.
- Frames are not persisted and there's no scrubbing UI. Frame history would add a `frame` event kind (seq + file path or ring-buffer index) to the same log; nothing else assumes events are small.

## Messaging and agent status
- `guilab poll [--timeout SECS]` blocks until a wake event, prints it and everything else since the previous delivery, and exits 0 (2 on timeout, still printing what happened). `--follow` keeps going with one line per wake event (passive events appended as `(meanwhile: ...)`), for Monitor-style tools.
- Messages carry images from the image store (`image-system-design.md`): events hold `ImageRef`s (id, canvas size, listing snapshot, marks bbox). **Pull, not push**: `poll` prints each image's listing plus a fetch hint (`guilab image ID --crop` the marks + 20 px), never a PNG. Every image a message references is held until its session ends. A human message without images also carries `screen`, the id of a capture taken as it was sent, pointer drawn in ("their screen as they sent it"): short messages refer to what the human looks at (`issues/message-context.md`'s idea, the cheap part).
- The viewer's drawings reach the store unbaked: `Freeze` captures (and holds) the base image and hands the viewer its id as the sketch's tag; on send, the markup marks become elements on a copy of that base (`Made::Human`, parent = the base). Text is baked into renderings like every other mark; the listing gives its position and box.
- The agent is either **working** (with a status text) or **waiting** for the human, one state per session, so the human always knows whether to wait or answer. `work "STATUS" [-m MSG] [--image ID|PATH]` sets it (and posts MSG); `done [MSG] [--image ID|PATH]` posts MSG, clears it and releases the lock. A file becomes a new image (one raster/SVG element); a PNG guilab rendered is refused with its id. `say` is gone (its error points to `work -m`/`done`).
- Rules (errors say what to run): `done` refuses while a human message is unread (a fresh agent replied right past one); `lock`/`input` need working; a blocking `poll` while working is an error unless something is pending (unread message, wake event) or `--timeout 0`; `--follow` is always allowed. A poll that shows a human message marks the agent working with status "read your message", so it must end with `done`.
- The server keeps it in `Slot::working` (status, start of this stretch of work) plus `Slot::last_agent` (last command); `ls` shows `working="..."`.
- The hidden `guilab debug message|input|revoke` acts as the human for tests. `debug message --draw ELEMENT...` captures the screen as the human and draws on it (like the viewer); `--image ID|PATH` attaches. The viewer's message box and `debug message` both go through `requests::human_message`. Human input goes through `Session::inject(.., InputSource::Human)`, which logs it; it's refused while locked.

## Viewer
Start with basic functionality. Don't build UI or features we aren't sure we need.

UI quality: egui means building our own small toolkit (menus, toolbars, dialogs…). Build each widget to feel like a normal desktop app, not subtly off: hover/pressed/disabled states, keyboard navigation and shortcuts, menus that close on outside click or Escape, consistent spacing, correct cursors. Make these pieces composable and reusable with sensible abstractions, scoped to this app (no general framework). Use a third-party egui crate only if it's genuinely good.

Theming: all colors, spacing, sizes, rounding, fonts and timings come from one theme module (`guilab-kit` `Theme`: named tokens, light and dark variants). Widgets never hardcode them, so a later theming pass changes values in one place. No user-settable themes. Light/dark follows the desktop's preference (the XDG portal `org.freedesktop.appearance color-scheme`, which GTK/libadwaita also use), defaulting to dark if unavailable, with a System/Light/Dark choice in the View menu.

Layout:
- **Top:** one tab per session (🔒 when locked).
- **Main area:** the session. The viewer's size changes the session's output size only through explicit controls (below) or the CLI. The human uses the app directly here, unless locked out (then input is dropped and the lock toast shows; releases of held keys/buttons still go through).
  - Zoom is host physical pixels per session pixel (100% = pixel-exact). Fit is the default and follows the window, capped at the larger of 1:1 and the session's logical size (so a scale-2 session on a 1x host shows pixel-exact, a scale-1 session on a 2x host at its normal size).
  - Top: a menu bar (File: save screenshot or the open drawing via the system save dialog, rfd: portal, else zenity, on a thread; Edit: undo/redo; View: zoom − / % (click: 100%) / +, Fit to window, session size, chat off/bottom/right, appearance System/Light/Dark), then session tabs (only with 2+ sessions). No status bar: nothing says a session is unlocked or locked until the human tries to use a locked app; then a toast "Agent using app" with Stop (revokes the lock). Toasts sit at the bottom of the view (`guilab_kit::toast`, one stack: the frozen-screenshot bar, later the editor's crop toast, lowest).
  - Mouse scheme: with "Use the app", plain clicks, drags, scrolling and touchpad gestures over the image go to the app. Scrolling that doesn't go to the app (drawing/Move tools, outside the image) moves the view per `NavMode`: ScrollZooms (wheel zooms at the pointer) or ScrollPans (two-axis scroll pans, pinch zooms at the pointer). `NavSetting::Auto` picks ScrollPans for smooth scrolling when the host offers pinch gestures, else ScrollZooms; a user setting may come later. Ctrl+scroll always zooms; middle-drag anywhere or any drag outside the image pans. A middle click that doesn't move still reaches the app (sent on release). Rejected: plain scroll to zoom over the app and space+drag (both take input the app needs).
  - Session size (per session tab, View menu): **Resize to window** sets the session's *logical* size to the view (host points; pixels = that × session scale) and fits, so the session scale changes sharpness, not how big things look. **Lock size to window** keeps doing that as the window resizes (throttled to 10/s) and disables zoom/pan. Size (W×H pixels) and scale (presets 1, 1.25, 1.5, 1.75, 2, or any 0.25-8) fields; changing the scale keeps the pixel size, or the logical size while locked to the window. **Resize handles** (edges, corners) just outside the image where there's room: drag resizes the output in session pixels with a size readout and a target outline, live at 10/s, the opposite side staying put.
  - An agent's lock freezes the size for the human: the size controls and handles are disabled and window resizes don't apply; the agent can still `output -s` (the view just fits it). On unlock or revoke, "lock size to window" fits again. Human resizes log `output` events marked as the human's (passive, like agent ones), with no overlay note.
  - Cursor over the image: the app's own (named shape, image or hidden, at its real size) when input reaches the app; otherwise a tool cursor, never the arrow, which would suggest input goes through (not-allowed while locked out, crosshair for drawing tools, grab where a drag pans).
  - Clipboard (text): the host's and the shown session's are bridged. A new host selection goes to the session; the session's changes go to the host only while the viewer has keyboard focus, so an agent's `clip set` or copy doesn't silently replace the human's desktop clipboard.
  - Host touch: touches that start on the image go to the app (with "Use the app"); elsewhere a finger acts as the pointer on the viewer's UI.
  - Without server-side decorations (e.g. GNOME), the menu bar doubles as the title bar (drag, double-click, window buttons) and the window edges resize.
  - Keys go to the session unless an egui text field has focus (message box, text annotation) or a drawing is open. Human input to a session counts as activity for its TTL.
- **Left edge:** a narrow drawing toolbar for diagramming, not art: use-the-app (no tool), move (drag marks; drag elsewhere pans the view), pen, box, ellipse, line, arrow, text (as a tool or by double-click with any tool), six colors (red, yellow, green, blue, white, black; picking one with no tool selected picks the pen). Nothing more; undo/redo live in the Edit menu and Ctrl+Z / Ctrl+Shift+Z (Ctrl+Y). One fixed stroke width and font size (3 and 18 logical px, scaled by the session scale).
- **Bottom:** the message box (Enter sends, Shift+Enter newline), queued thumbnails next to it, and above it a feed: human and agent messages (with image thumbnails, full size on hover) and each agent command and status change (`working: ...`, `done`) as one gray line, so you can see what the agent is doing. While the agent works, the feed ends in a status line: pulsing dots, the status in the agent's color, the time it's been working, and after 2 minutes without a command a dim "no guilab activity for Nm" (compiles are normal, so it never clears the status). `markup::Chat::set_status` takes a plain `Status {text, elapsed, quiet}`; the server builds it per frame. A drag handle resizes the panel. The feed is built from the session log, so it's the same after hide/show.

Drawing flow:
- With a tool selected, pressing on the image starts a drawing: the viewer asks the server for a screenshot (whole output, no cursor, forced opaque) and shows it frozen under the marks. While a tool is selected or a drawing is open, pointer input over the image never reaches the app; zoom/pan work as usual (plain scroll also zooms). While a drawing is open, keys stay in the viewer (Ctrl+Z undo, typing text), and a bar over it says "Drawing on a frozen screenshot" with Queue and Discard.
- Text: click (text tool) or double-click (any drawing tool) opens a box at that point (focus is taken after the click is released, else the release steals it); Enter or clicking elsewhere commits, Esc cancels. Text wraps at `WRAP_EMS` font sizes or the image's right edge (the box moves left if that leaves under 6 ems); growing past the bottom pushes it up. The wrap width is stored in the mark (`Kind::Text(pos, text, width)`), ready for resize handles later. Backing: translucent black, or translucent white behind very dark text (only black in the palette).
- "Queue" composites the drawing into a thumbnail next to the message box (× deletes it, hover shows it big). All queued drawings, plus one still open, go with the next message, which may have no text. Queue, Send and Discard return to the use-the-app tool.
- Marks are stored in session pixels and drawn with egui; the composite is rendered on the CPU by tessellating the same egui shapes (`guilab-markup` `Renderer`), so it matches the screen exactly with no GPU or extra dependency.
- Annotation + queue + chat feed live in `crates/markup` (`guilab-markup`), which depends only on egui: screenshot (`ColorImage`) in; composited images, text notes and messages out. No compositor, IPC or session types. Its `compose` example and unit tests use it without guilab.

Text in drawings: an earlier test found agents misread notes whose baked text box covered the label it pointed at. The element listing now gives every text's position and box as text, and agents fetch the pixels cropped to the marks, so text is baked again (user's decision, `issues/image-system.md`).

## Screenshots
- Every screenshot is a new image in the store (a raster element filling the canvas; unchanged frames reuse the raster). Agent screenshots take cursor on/off, settle-wait on/off, `--crop` (the image's crop; the full raster is kept) and `--max` (PNG only). The default waits for the app to finish drawing, includes no cursor, and captures the whole output. The PNG goes to `img/<id>.png` in the session dir, or `-o PATH`.
- Human screenshots are always whole output with no cursor, taken when the action triggers them.

## CLI
- Built for agents first. No compatibility with xdotool/wdotool. Ship a short skill doc.
- **Input data is positional args and flags, never JSON**, so it's terse and needs no quoting. Input actions chain within one command (like wdotool) so held buttons and modifiers work.
- Output is compact text made for agents to read. `--json` gives structured output for scripts.
- All coordinates agents see or give are output pixels, i.e. screenshot pixels, at any scale.
- Errors are short and say what to do.
- Rough command set (to be refined during implementation):
  - server: `server [--show] [--stop] [--wait] [--idle-exit SECS]`, `show` (`-S NAME` picks the tab), `hide`
  - sessions: `new [NAME] [-s WxH] [--scale S] [--ttl SECS] [-x]`, `end`, `ls`; `-S NAME` / `--session NAME` on any command
  - apps: `run -- CMD...`, `kill [ID]` (replies once the apps are gone, up to 5 s, so `kill && run` doesn't race a single-instance app), `ps` (with exit status). No restart or watch mode: `build && guilab kill && guilab run ...` is enough.
  - control: `lock`, `unlock`, `output [-s WxH] [--scale S]` (no args: show)
  - input chain: `input ACTION...`, grammar and docs in `guilab input --help` (`proto/src/input.rs` `HELP`): `move X Y [MS]` (MS = glide), `down/up [BTN]`, `click [BTN] [N]`, `scroll DX DY` (wheel notches), `scrollpx DX DY` (touchpad), `key CHORD`, `keydown/keyup KEY`, `type TEXT`, `touch down|move|up ID [X Y] [MS]`, `tap X Y`, `pinch SCALE [DEG]`, `swipe DX DY [FINGERS]`, `on ID|output` (surface-local pixels from the surface's `tree` origin; events still go to whatever is on top), `sleep MS`. Chains are parsed and key names checked before anything runs. Sleeps don't block the server; a session's chains run one at a time in order. Replies with the pointer position, surface under it and keyboard focus.
  - inspect: `log [--since 5m|14:05] [--after SEQ] [--kind K,..] [-n N]` (default newest 100), `tree` (toplevels topmost first, with popups and subsurfaces nested; X windows as `x11` / `x11_popup` with xid, class, title, pid (`_NET_WM_PID`, else X-Resource); all with ids and pixel geometry), `screenshot [-o PATH] [--cursor] [--no-settle] [--crop R] [--max WxH]`, `image ID [-o] [--crop R|none] [--max] [--no-marks] [--list [--points]]`, `image make ...` (skill doc "Images")
  - clipboard: `clip get`, `clip set [TEXT]` (stdin without TEXT); text only, clipboard selection only (no primary)
  - messaging and status: `poll [--follow] [--timeout SECS] [--wake K] [--passive K]`, `work STATUS [-m MSG] [--image ID|PATH]`, `done [MSG] [--image ID|PATH]`
