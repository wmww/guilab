# Viewer window: how it works and what to know

Built in plan steps 6-7 (`crates/viewer`, `crates/markup`, `crates/kit`, `crates/server/src/viewer.rs`). Versions: sctk 0.20, egui/egui_glow 0.35 (glow 0.17), smithay pinned master.

## Shape
- Our own sctk client on a separate `Connection` (not smithay's winit backend: its renderer dies with the window, and winit refuses a second `EventLoop` per process, so show/hide/show would be impossible).
- The one `GlesRenderer` (render node, GBM `EGLDisplay`) draws sessions and the viewer. On a pixman server the viewer has its own `software_gles()` (llvmpipe, `Shown::soft`, shm presentation) and the current session's frame comes as a `ColorImage` (`SessionFrame::image`, read back when `frame_seq` changes, an egui texture via `Gfx::cpu_texture`) instead of the GPU mirror; `with_renderer` picks the right one. Test: `viewer::click_through_pixman`. Hiding drops the window, connection, buffers, egui context and painter; the renderer stays.
- `connect` (socket connect + registry roundtrip) runs on a helper thread; the result comes back over a calloop channel tagged with an attempt number, so stale results after hide/show are ignored. A 10 s deadline fails the pending `show`.
- `source.rs` replaces calloop-wayland-source: that one returns host I/O/protocol errors from `EventLoop::dispatch`, which would stop the server. Ours reports `HostEvent::Lost` once and removes itself; the server then hides the viewer. Note `Connection::protocol_error()` is checked after dispatch (a protocol error leaves nothing to read).
- Drawing happens from the server tick, only when the host is ready (configured, frame callback back) and something changed: host input, resize/scale, egui's repaint request, or the signature of the shown sessions (names, lock states, sizes, cursor, the current session's `frame_seq`). New input runs the UI even while waiting for a frame callback (so actions apply without waiting); egui texture deltas from frames that couldn't be presented are kept for the next one. GTK4's fading text caret makes a focused entry commit continuously, so the viewer redraws at the frame rate then; that's the app, not us.

## Presentation (host.rs)
- dmabuf: `Swapchain<GbmAllocator>` (ARGB8888) with modifiers from the host's default `zwp_linux_dmabuf_feedback_v1` format table ∩ `egl_context().dmabuf_render_formats()`, only if the feedback's main device is our GPU (render and card nodes compared via `/sys/dev/char/M:m/device`). Each slot caches its `wl_buffer` (`create_immed`) in userdata, destroyed with the slot; slots stay busy until `wl_buffer.release`.
- shm fallback (no v4 feedback within 500 ms, other GPU, no common modifier, or `GUILAB_VIEWER_SHM=1` in the server's env): render to an offscreen `GlesTexture`, `copy_framebuffer` + `map_texture`, swizzle RGBA → BGRA into an sctk `SlotPool` buffer (max 3).
- egui_glow draws GL-style (row 0 at the bottom); the surface has `set_buffer_transform(Flipped180)` (a vertical flip). Both paths share the same memory layout, so the same transform works.
- HiDPI: `wp_fractional_scale_v1` + `wp_viewporter` when available (buffer = logical × scale, viewport destination = logical size), else integer `wl_surface` buffer scale. egui `pixels_per_point` = scale.
- egui is painted inside a smithay frame (`frame.with_context`), after its clear. Afterwards `Gfx::paint` resets the GL state egui leaves (scissor, program, VAO, buffers, texture, blend func) so smithay's next session render isn't affected.

## egui on smithay's context (gfx.rs)
- smithay's glow (0.16) and egui_glow's (0.17) differ, so we make our own `glow::Context` on the same EGL context via `smithay::backend::egl::get_proc_address`.
- **egui_glow deletes every texture registered with it** when freed or replaced (`free_texture`, `replace_native_texture`, `destroy`). So session textures are never registered directly: each is a "mirror", an egui-owned texture that `glBlitFramebuffer` fills from the smithay texture when the session's `frame_seq` changed (only the current tab's). Mirror filter: NEAREST at ≥ 2 host pixels per session pixel, else LINEAR.
- egui debug builds outline unaligned widgets in red (`style.debug.show_unaligned`); we turn that off.
- `ctx.run_ui` may run several passes; the UI consumes host input only in the first (it's moved into the closure's first call).

## Input (host.rs, ui.rs)
- Host input is one ordered list (`HostInput`: egui events and raw evdev keys), so "click, type, click" stays in order when one frame has all of it. egui gets the egui events (minus Key/Text when keys go to the session); the UI walks the full list.
- `HostState::take_input` hands out one batch per UI pass: it ends after a button event, before a press that follows motion, before a touch start (in a pass of its own) and after a touch end (where a touch goes, app or UI, depends on the state the input before it left). So keys typed right after a click are routed by the focus that click gave (keys go to the session unless egui wants them, decided per pass), a click arriving with the pointer's first move isn't lost (egui needs a hover pass), and egui sees one click per pass. Leftover input keeps `has_input` true, so the next tick runs the next batch. Scripted viewer tests need no sleeps between steps for this.
- `Chat` decides Enter-sends after the text box took the pass's typing ("type hello key Return" in one pass sends "hello").
- Keys are forwarded as raw evdev codes (+8 = xkb code), so the session keeps its own keymap. Modifiers reach egui via `update_modifiers`.
- The UI tracks the buttons and keys it pressed in a session and releases them on tab switch, lock (blocked), keyboard leave and hide.
- Host touch (`wl_touch`, `HostInput::Touch`): `Viewer::route_touches` sends a touch that starts on the image with "Use the app" (`ViewerUi::touch_to_app`, last frame's rect) to the UI, which forwards it as session touch (each followed by a touch frame); the first other touch is turned into egui pointer events (tap = click, drag = drag), more fingers are dropped.
- Pinch and swipe (`zwp_pointer_gesture_*_v1`, bound by hand) arrive as `HostInput::Gesture`. A gesture that begins over the image with "Use the app" goes to the app whole; otherwise a pinch zooms the view at the pointer and a swipe does nothing.
- Key repeat: the host compositor leaves repeat to clients, so `HostState::tick_repeat` (called each server tick via `wants_draw`) repeats the held key for egui only, at the host's `repeat_info`. Raw keys forwarded to sessions never repeat; the session's apps repeat themselves (see design.md).
- Pointer leave: the UI tracks which session last got motion (`pointer_in`) and sends `Input::Leave` when the pointer leaves the image, a tool takes over, the lock blocks, the tab changes or the window loses the pointer. Cursors: see below.
- Wheel vs touchpad: axis events with value120/discrete or source Wheel become egui `Line` units (notches), else `Point`. Forwarded wheel = 15 logical px per notch (like agent `scroll`); smooth scroll is scaled so content follows the fingers.

## Sizing (sizing.rs, ui.rs)
- `Action::Resize { size, scale }` → server `requests::set_output(.., key: None)` (ignored while locked; logs `output` with `human: true` only if something changed). The agent path uses the same function with its key.
- `sizing::fit_pixels(view, scale)`: floor(view points) × scale, rounded. "Lock size to window" (`Sizing::follow`) runs `follow_window` each frame before `view()`; zoom forced to fit, zoom/pan inputs ignored (`fixed`).
- Handles: `handle_at` (10 pt band outside the image, only where it fits in the view); a drag (`Resizing`, in `ViewerUi` like `panning`) freezes the zoom and sets the pan each frame so the anchor (opposite edge/corner) stays put while the frames catch up; restores fit on release. Input loop: handle presses come before the off-image pan.
- At matching host/session scales a fitting session is pixel-exact (tested at 1.5: `viewer::pixel_exact_at_fractional_scale`). Fractional scaling checked by eye with GTK4, Qt6 (PySide6) and Chromium at 1.25/1.5 incl. live changes: crisp.

## Clipboard (clipboard.rs, server viewer.rs)
- `HostClipboard` (sctk data device, text mimes): `set_clipboard` takes the host selection with the last input serial (keyboard enter, key or button press; queued until there is one), `take_clipboard` returns text read (on a thread) from a new selection someone else made. Our own selection's echo is ignored while our source is alive (it's cancelled before someone else's selection arrives).
- Server `ClipBridge` (per shown viewer, current session only): host text → `clip_set`; `Session::clip.seq()` changes → `clip_get` (pipe read on a thread) → host, only while the host window is focused; `last` stops ping-pong. Test: `viewer::clipboard_bridge`.

## Window decorations
- The host decides (xdg-decoration; sctk reports `DecorationMode::Client` without it, e.g. GNOME). With client-side decorations (`HostState::csd`; `GUILAB_VIEWER_CSD=1` in the server's env forces it, for testing on our SSD-only host) the menu bar's free part (`MenuBar::show` returns it) becomes a title bar: drag = `xdg_toplevel.move`, double-click = maximize toggle, minimize/maximize/close buttons; a 5 pt border resizes (`border_presses` turns a press there into `xdg_toplevel.resize`, using the last press serial). Tested against guilab as host: move (floating viewer), close, cursors.

## Cursors
- Over the app with input going through: the app's own cursor. The compositor (`cursor.rs`) gives `AppCursor`: Named (cursor-shape protocol), Hidden, or Image (a `wl_pointer.set_cursor` surface rendered to RGBA at the output scale by `Gpu::render_surface`, lazily, once per `cursor_seq` change; animated cursors get frame callbacks each tick, and cursor commits don't count for settle). The server converts it to `HostCursor` once per change (`Shown::cursor`).
- Host side (`HostState::set_cursor`): named → `wp_cursor_shape_v1`; image → an shm buffer on our own cursor surface, viewport destination = image size / its scale (not the viewer's zoom: real cursors aren't zoomed); hidden → null surface. `set_cursor` needs the *enter* serial (smithay rejects others outside a grab).
- Over the image when input doesn't go through: blocked by the lock → NotAllowed; drawing tools → crosshair/text (canvas); Move tool and a frozen screenshot with "Use the app" → Grab (drag pans), AllScroll over marks (Adwaita draws `move` as the arrow), Grabbing while panning. Never the arrow there.
- The UI decides via egui's cursor; for an image cursor it sets `Default` and `ViewerUi::host_cursor` swaps in the image if nothing overrode it.
- `screenshot --cursor` draws the same cursor at the pointer (named shapes from the xcursor theme, `XCURSOR_THEME`/`XCURSOR_SIZE`, default `default`→Adwaita), which is how tests check the host's cursor (`viewer::app_cursors`, app `gtk_cursors.py`).

## Chat and drawing (ui.rs, markup)
- Panel order matters in egui: tabs (top), toolbar (left, full height), chat (bottom), then the central session view. The toolbar must come before the chat panel or a tall chat panel cuts it off.
- The UI only runs when the viewer draws. When it ran on input but couldn't present (waiting for a frame callback), `Viewer::draw` sets `host.dirty` so the new state still gets shown.
- The frozen screenshot arrives one frame after the press (`Action::Freeze` -> server -> `set_screenshot`); the first mark is already being dragged on the live image meanwhile.
- Feed scrolling: egui's `stick_to_bottom` lost track after `scroll_to_cursor`; `Chat` tracks "at the end" itself from the `ScrollArea` output and follows new items only then (and after sending). A frame that asked to scroll to the end counts as at the end (the scroll lands next frame).
- The text box uses a non-wrapping layouter: computing its width before the TextEdit sees the frame's typed text made it wrap.

## Testing
- Host = a second guilab server's session (tests: `tests/it/viewer.rs`; it pins the coordinate mapping by moving the host pointer and reading the viewed session's human motion event). Lab commands drop `WAYLAND_DISPLAY`, so a test can never open on the real desktop.
- `draw_and_send` clicks fixed viewer positions (toolbar at x=19: box y=133, text y=262 with one session (no tab bar); message box near the bottom). Layout changes move them. Other viewer tests find the host->session mapping by probing two points (the view may be zoomed).
- egui gotchas: `consume_key` ignores Shift (use `consume_plain_enter` for Enter-sends); a TextEdit with a custom `.frame()` ignores `.margin()`.
- Manually: `GUILAB_DIR=$XDG_RUNTIME_DIR/glv-h guilab new host -s 1400x900`, then `GUILAB_DIR=$XDG_RUNTIME_DIR/glv-v WAYLAND_DISPLAY=$XDG_RUNTIME_DIR/glv-h/s/host/wayland-0 guilab show` (the viewed server), drive the host session with `input`, screenshot it. Strip the real `WAYLAND_DISPLAY` from every other command.
- The real desktop's `WAYLAND_DISPLAY` is usually set in agent shells; never run `guilab show` without overriding it.
- Input overlay (`viz.rs`): the compositor records input that reaches apps, agent and human alike, in `Session::viz` (`guilab_proto::viz::VizLog`, a bounded ring with seqs; keys labeled there since it has the keysym and modifiers; `output` changes add a note). The viewer reads new entries for the current session each frame (`SessionFrame::viz`, part of the redraw signature) and paints: soft glow at the pointer (colors by input type, same for agents and humans: pointer blue, touch green, keys purple; stays until a `Leave`, then fades), ripple per press, chevrons per wheel notch (per axis, stepping out in the scroll direction), smooth scrolling stretches the glow into a droplet trailing opposite the scroll (tail length ∝ speed, uncapped), a thin dim hover trail and a brighter, thicker drag path (held until release), each drawn as one feathered triangle strip (no dots at joints), a brief flash on press, green rings for touch points, and a key/notes stream bottom right. The UI font lacks arrows/⏎/␣, so those keys are drawn as shapes (`key_icon`).
- Menus: `guilab_kit::menu` is the one menu bar widget (flat edge-to-edge titles, faint hover / stronger open fill; a press on a title opens, hovering another title while open switches (only on pointer motion, so Left/Right aren't undone), releasing over an item activates it (press-drag-release works), Esc / press outside / press on the open title closes; Up/Down/Home/End move the highlight over enabled items, Enter/Space activate, Left/Right switch menus, keys applied in order; a focused field in a custom row keeps its keys; full-width flat items, radios, checks, headings, notes, custom rows; width = widest row from the previous frame). Use it for any future menu bar rather than egui's `MenuBar`. While a menu is open, keys go to egui (`keys_to_egui`), not the session, and a press outside only closes it (`view` ignores presses when a menu was open at the frame's start).
- Theme: `guilab_kit::theme::install` on the context in `Viewer::new`; every widget color/size comes from `Theme::get`. Light/dark: `ViewerUi::theme` (View > Appearance) → `ctx.set_theme`; System uses `portal::color_scheme()` (portal value 1 dark, 2 light, 0/none → dark), polled each `wants_draw` (an atomic), a change redraws. egui clicks don't give focus (only Tab does), so focusable custom widgets don't steal keys from the session.
- Light/dark overlay colors: `Session::color_under_pointer` averages a 9x9 patch of the last frame around the pointer via a small region readback (`Frame::read_rgba_region`; cached per (viz seq, frame seq), at most every 100 ms). `Session::sample_rgb` is the general helper (e.g. a future color picker). The server passes it in `SessionFrame::under_pointer`; luminance > 185 eases (0.3 s) toward the deeper `LIGHT_BG` palette. Key chips: 42.5 px faux-bold text, equal min widths (wider for drawn symbols), centered.
